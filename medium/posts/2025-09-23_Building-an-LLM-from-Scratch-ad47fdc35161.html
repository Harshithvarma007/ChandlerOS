Tokenization — Turning Poems Into Numbers

Okay, we’ve got our dataset — 223,000 characters of pure poetic chaos.

But here’s the thing: LLMs don’t understand words.

In fact, they don’t even understand letters. What they really speak is numbers.

So before we can whisper Shakespeare into our model’s ear, we need to translate poetry into math.

That’s where tokenization comes in: converting text into tokens (IDs).

Tokenization Approaches

There are a few different ways to chop up text:

Character-level

  • Each character gets its own ID.
  • Simple, tiny vocabulary… but sequences get very long.

Word-level

  • Each word is a token.
  • Nice and compact, but the vocab explodes and unseen words cause trouble.

Subword-level

  • Words get broken into chunks (e.g., “unbelievable” → “un” + “believe” + “able”).
  • Best of both worlds — this is what the big guys like GPT and BERT use.

Since we’re building our baby LLM, we’ll keep it simple with a character-level tokenizer.

That means every single character — from a to Z, from spaces to punctuation—gets its own unique ID.

Building Our Character-Level Tokenizer

Let’s create two magical dictionaries:

  • encode: character → integer ID
  • decode: integer ID → character

This way we can move back and forth between poetry and numbers like bilingual wizards.

# create a mapping from characters to integers
stoi = { ch:i for i,ch in enumerate(chars) }
itos = { i:ch for i,ch in enumerate(chars) }
encode = lambda s: [stoi[c] for c in s]  # encoder: string -> list of ints
decode = lambda l: ''.join([itos[i] for i in l])  # decoder: ints -> string
print('encoder :', encode("love this tokenizer"))
print('decoder :', decode(encode("love this tokenizer")))

Output:

encoder : [62, 65, 72, 55, 1, 70, 58, 59, 69, 1, 70, 65, 61, 55, 64, 59, 76, 55, 68]
decoder : love this tokenizer

Boom 💥 — text to numbers and back again.

Our model doesn’t care about “love” or “tokenizer,” it just sees [62, 65, 72, …].

Block Size — Teaching Our Model How Much to “Read”

So, we’ve tokenized our poems into numbers. Great!

But here’s the thing: if we throw the entire dataset at the model in one go, it’ll just drown in numbers like me trying to read my grandma’s WhatsApp forwards.

We need to be smarter about it.

Train / Validation Split

First, we divide our dataset into two buckets:

  • 90% Training Data — this is what the model studies from.
  • 10% Validation Data — this is the pop quiz: data the model hasn’t seen, so we can check if it actually learned anything instead of just memorizing.
# Let's now split up the data into train and validation sets
n = int(0.9*len(data))  # first 90% will be train, rest val
train_data = data[:n]
val_data = data[n:]

Simple and effective. Our baby LLM now has a school curriculum.

Block Size (a.k.a Context Window)

Now comes the fun part: how much text should the model “see” at once?

This is called the block size or context window.

  • Small block size → The model only learns short-term patterns.
  • Large block size → It can capture longer dependencies, but it eats up way more memory.

Think of it like reading a book:

  • If I only give you 5 words, your guess at the next word is shaky.
  • If I give you 50 words, your guess is way better.

For our experiment, we’ll keep it humble with:

block_size = 8
train_data[:block_size+1]

Output:

tensor([64, 51, 64,  0,  1,  1,  1,  1,  1])

So our model sees 8 tokens at a time and tries to predict the 9th token.

Input vs Target

Here’s how training works:

  • Input (x): a sequence of tokens.
  • Target (y): the same sequence but shifted by one position.

So the model is always learning to predict the next token.

Example:

  • Input (x): "hell" → [h, e, l, l]
  • Target (y): "ello" → [e, l, l, o]
x = train_data[:block_size]
y = train_data[1:block_size+1]
for t in range(block_size):
    context = x[:t+1]
    target = y[t]
    print(f"when input is {context} the target: {target}")

Output (sample):

when input is tensor([64]) the target: 51
when input is tensor([64, 51]) the target: 64
when input is tensor([64, 51, 64]) the target: 0
...

It’s like training a psychic:

“Given this chunk of text, can you predict the next character?”

The model doesn’t see the future — it just gets really good at guessing it.

Creating Batches

At this point, we’ve got a giant pile of text data, and honestly, throwing it all at once into our model would be like asking someone to eat 3 years’ worth of meals in one sitting. Not only impossible, but also very unhealthy (for both humans and GPUs).

So instead, we train in mini-batches — small, manageable chunks of data.

Think of it like going to the gym:

  • You don’t lift 500kg on day one (unless you’re The Rock).
  • Instead, you break it down into smaller sets and reps, slowly building strength.

That’s exactly what mini-batches do for our model. They:

  • Speed up training
  • Help the model generalize better instead of just memorizing data

The Helper Function

Here’s our batch-maker function. It randomly grabs slices of data (inputs and their targets) and bundles them neatly for the model.

torch.manual_seed(42)
batch_size = 4   # how many sequences we process in parallel
block_size = 8   # max context length
def get_batch(split):
    # pick training or validation data
    data = train_data if split == 'train' else val_data
    # random starting positions
    ix = torch.randint(len(data) - block_size, (batch_size,))
    # inputs (x) and targets (y)
    x = torch.stack([data[i:i+block_size] for i in ix])
    y = torch.stack([data[i+1:i+block_size+1] for i in ix])
    return x, y
# generate a sample batch
xb, yb = get_batch('train')
print("inputs:\\n", xb.shape, xb)
print("targets:\\n", yb.shape, yb)

This is how the model slowly learns “what usually comes next.”

From Batches to Brains: The Bigram Model

So far, we’ve been carefully chopping our dataset into mini-batches 🍱 and feeding them into the model like little snacks. But right now, our model is basically… nonexistent. It’s like inviting guests to dinner without actually cooking anything.

Time to cook.

We’ll start small, with a Bigram Language Model. Think of this as the “baby’s first language model.”

Here’s the idea:

  • It looks at one character and tries to guess the next character.
  • No deep reasoning, no context beyond a single step.
  • Imagine someone trying to finish your sentences, but they only remember the last word you said. (They’re not very smart yet, but hey — it’s a start!).

Later, we’ll upgrade this into transformer territory, but first, let’s get the basics.

Loss Function — Teaching the Baby to Speak

How do we know if our baby model is learning? Enter Cross-Entropy Loss.

  • High loss → the model is babbling nonsense
  • Low loss → it’s starting to say real words (or at least coherent sounds).

In mathematical terms, cross-entropy measures how far off our predictions are from the truth. In human terms, it’s like grading the model’s guesswork on how “surprised” it should be.

The Code — Building the Bigram Model

Here’s our first model:

import torch
import torch.nn as nn
from torch.nn import functional as F
torch.manual_seed(42)
class BigramLanguageModel(nn.Module):
    def __init__(self, vocab_size):
        super().__init__()
        # each token directly maps to the logits for the next token
        self.token_embedding_table = nn.Embedding(vocab_size, vocab_size)
    def forward(self, idx, targets=None):
        # idx and targets are both (B,T) tensor of integers
        logits = self.token_embedding_table(idx)  # (B,T,C)
        if targets is None:
            loss = None
        else:
            B, T, C = logits.shape
            logits = logits.view(B*T, C)
            targets = targets.view(B*T)
            loss = F.cross_entropy(logits, targets)
        return logits, loss
    def generate(self, idx, max_new_tokens):
        # idx is (B, T) array of indices in the current context
        for _ in range(max_new_tokens):
            logits, _ = self(idx)
            logits = logits[:, -1, :]   # only look at last step
            probs = F.softmax(logits, dim=-1)
            idx_next = torch.multinomial(probs, num_samples=1)
            idx = torch.cat((idx, idx_next), dim=1)
        return idx

Now let’s try it out:

m = BigramLanguageModel(vocab_size)
logits, loss = m(xb, yb)
print(logits.shape)
print(loss)
print(decode(m.generate(idx = torch.zeros((1, 1), dtype=torch.long),
                        max_new_tokens=100)[0].tolist()))

Setting Up the Optimizer

Now, how do we teach this baby to improve? With an optimizer.

We’ll use AdamW, a smarter cousin of Adam that helps prevent overfitting (think of it as giving the baby a personal trainer ).

  • The parameters are the knobs the model can turn.
  • The learning rate (1e-3) is how fast or slow it makes adjustments.
# create a PyTorch optimizer
optimizer = torch.optim.AdamW(m.parameters(), lr=1e-3)

In simple words: the optimizer is like a GPS recalculating your route every time you take a wrong turn, nudging you closer to your destination.

Training the Model

Alright, we’ve built the baby brain (Bigram model), but right now it’s just drooling random symbols onto the page. Time to actually teach it something.

Training a model is like sending our baby to school: we repeatedly show it examples, correct its mistakes, and hope it comes back a little smarter each day.

Here’s what happens inside the training loop:

  1. Batch sampling — grab a mini-batch (xb, yb) of input-target pairs.
  2. Forward pass — run it through the model to get predictions (logits) and compute the loss.
  3. Zero gradients — clear old gradient info (think: erase the previous “chalkboard”).
  4. Backward pass — calculate how wrong the model was, and where to adjust.
  5. Optimizer step — tweak the weights just a little, guided by AdamW.

We repeat this for many steps. Each step is like one lesson. The more lessons, the smarter the model (well, usually 😅).

batch_size = 32
for steps in range(100):  # increase steps for better results
    # sample a batch of data
    xb, yb = get_batch('train')
    # evaluate the loss
    logits, loss = m(xb, yb)
    optimizer.zero_grad(set_to_none=True)
    loss.backward()
    optimizer.step()
print(loss.item())

Example output:

4.634866237640381

A decreasing loss means the model is actually learning.

Now comes the exciting part: making the model speak.

Here’s the recipe:

  • Start with a seed input (torch.zeros((1,1)) → basically telling the model “begin from nothing”).
  • Call the generate() function, asking it for up to 500 new tokens.
  • Decode those tokens back into human-readable text.
print(decode(m.generate(
    idx = torch.zeros((1, 1), dtype=torch.long),

Matrix Multiplication as Weighted Aggregation

Let’s pause for a second. Up to now, we’ve been looping over time steps to compute averages. It works… but it feels a bit like washing clothes by hand when you’ve got a washing machine right next to you. It’s slow, repetitive, and doesn’t scale well.

So what if we let linear algebra do the heavy lifting?

The Setup

We start with a special kind of matrix:

  • Matrix a → a lower-triangular matrix where each row sums to 1. Think of it as a recipe book: each row tells us how much weight to assign to past values.
  • Matrix b → our actual data (the "ingredients").
  • Multiply a @ b → and boom, we get Matrix c, which is just a beautifully aggregated dish made from weighted combinations of rows in b.

Here’s the magic in action:

torch.manual_seed(42)
a = torch.tril(torch.ones(3, 3))
a = a / torch.sum(a, 1, keepdim=True)
b = torch.randint(0,10,(3,2)).float()
c = a @ b
print('a='); print(a)
print('--')
print('b='); print(b)
print('--')
print('c='); print(c)

Outputs:

a =
[[1.0000, 0.0000, 0.0000],
 [0.5000, 0.5000, 0.0000],
 [0.3333, 0.3333, 0.3333]]
b =
[[2., 7.],
 [6., 4.],
 [6., 5.]]
c =
[[2.0000, 7.0000],
 [4.0000, 5.5000],
 [4.6667, 5.3333]]

Key Insight: Each row of a acts like a chef mixing ingredients with just the right proportions. The result? c is a smoothed, aggregated version of b.

From Example to Sequences

Now let’s scale this idea to sequences of data.

Imagine we’ve got:

  • Batch size (B): 4 → four sequences (think four different customers).
  • Time steps (T): 8 → each sequence has 8 moments in time.
  • Channels ©: 2 → at each moment, we’ve got two features.

Shape of our input: [4, 8, 2].

torch.manual_seed(42)
B,T,C = 4,8,2
x = torch.randn(B,T,C)
x.shape
torch.Size([4, 8, 2])

Version 1: The “By Hand” Approach

We compute the cumulative mean by brute force:

xbow = torch.zeros((B,T,C))
for b in range(B):
    for t in range(T):
        xprev = x[b,:t+1]  # all steps up to t
        xbow[b,t] = torch.mean(xprev, 0)

This works, but it feels… manual. Like a long road trip where you stop at every single gas station just to check if you’re still on track.

Version 2: Matrix Multiplication to the Rescue

Here’s the slick trick: we replace those loops with a lower-triangular weight matrix.

wei = torch.tril(torch.ones(T, T))
wei = wei / wei.sum(1, keepdim=True)
xbow2 = wei @ x   # (B, T, T) @ (B, T, C) -> (B, T, C)

And just to be sure:

torch.allclose(xbow, xbow2)
True

✅ They match perfectly! Both give the same result — one is clunky, the other is smooth linear algebra.

Why this matters: Neural networks thrive on matrix multiplications. By rewriting our problem in this form, we’ve aligned with how GPUs (and deep learning frameworks) actually work. This is why attention mechanisms, transformers, and modern LLMs can scale — no hand-washing loops, just elegant parallel math.

Softmax and Self Attention

So far, we’ve been averaging past values using fixed weights — first with loops, then with matrix multiplication. That’s neat, but it’s also a bit rigid. Every past token is treated equally (like every friend in a group project getting the same grade, even if only one actually did the work 👀).

But language isn’t like that. Sometimes the current word really cares about the one just before it, and sometimes it cares about something much earlier in the sequence. We need flexibility.

Enter softmax weighting.

Version 3: Using Softmax

Instead of forcing equal weights, we let softmax assign importance dynamically:

# version 3: use Softmax
tril = torch.tril(torch.ones(T, T))
wei = torch.zeros((T, T))
wei = wei.masked_fill(tril == 0, float('-inf'))
wei = F.softmax(wei, dim=-1)
xbow3 = wei @ x
torch.allclose(xbow, xbow3)

✅ And yes, this still matches our earlier results.

How it works:

  • Lower-triangular mask → ensures each token can only see itself + past tokens (no peeking ahead in the exam!).
  • Masked fill with -inf → makes sure future positions vanish when passed through softmax.
  • Softmax → converts each row into probabilities, telling us how much attention to pay to each past token.
  • Matrix multiply → weighted aggregation, just like before, but now with learned emphasis.

This is the first real taste of attention: not just averaging history, but choosing which history matters most.

Leveling Up: Self-Attention

Softmax weighting was the appetizer. Now, let’s move to the main course: self-attention.

Here’s the idea: instead of manually deciding weights, the model learns them using queries, keys, and values.

  1. Linear projections: Transform the input x into three versions — keys (k), queries (q), and values (v).
  2. Similarity check: Compare q with k using a dot product → this gives raw attention scores.
  3. Masking: Prevent tokens from looking into the future.
  4. Softmax: Normalize scores into probabilities.
  5. Weighted sum: Combine values (v) based on those probabilities → each token builds a new representation of itself, informed by its context.
torch.manual_seed(42)
B,T,C = 4,8,32
x = torch.randn(B,T,C)
head_size = 16
key = nn.Linear(C, head_size, bias=False)
query = nn.Linear(C, head_size, bias=False)
value = nn.Linear(C, head_size, bias=False)
k = key(x)   # (B, T, 16)
q = query(x) # (B, T, 16)
wei = q @ k.transpose(-2, -1) # similarity (B, T, T)
tril = torch.tril(torch.ones(T, T))
wei = wei.masked_fill(tril == 0, float('-inf'))
wei = F.softmax(wei, dim=-1)
v = value(x)
out = wei @ v
out.shape
torch.Size([4, 8, 16])

Understanding the Attention Matrix

Let’s peek at one attention matrix (wei[0]):

  • Row 0 → [1.000, 0, 0, ...] → Token 1 only attends to itself.
  • Row 1 → [0.1905, 0.8095, 0, ...] → Token 2 splits attention: 19% on Token 1, 81% on itself.
  • Row 3 → [0.1288, 0.3380, 0.1376, 0.3956, ...] → Token 4 blends across tokens 1–4.

Each token decides who to listen to and by how much. That’s the magic of self-attention: flexible, dynamic context-building.

Scaled Dot-Product Attention

One final piece before Transformers really start to shine: scaling.

When we compute q @ k.T, the dot products can get too large, making softmax overly confident (almost one-hot). That kills diversity in attention. To fix it, we scale by 1 / sqrt(head_size).

k = torch.randn(B,T,head_size)
q = torch.randn(B,T,head_size)
wei = q @ k.transpose(-2, -1) * head_size**-0.5

Why scale?

  • Without scaling → softmax collapses, focusing on just one token.
  • With scaling → smoother, richer distributions of attention.

It’s like grading on a curve in a classroom : scaling keeps scores reasonable so nobody dominates unfairly.

The Takeaway

  • Version 1 → manual averaging with loops.
  • Version 2 → matrix multiplication makes it scalable.
  • Version 3 → softmax adds dynamic importance (proto-attention).
  • Version 4 → self-attention with queries, keys, and values = the true Transformer superpower.
  • Scaling → the subtle trick that makes it all stable.

Layer Normalization (LayerNorm1d)

Up until now, we’ve been teaching our model how to look back in time, weigh history, and focus on what matters. But there’s one big problem: models can get a little… unstable.

Enter normalization, the yoga teacher of neural networks . It calms things down.

BatchNorm vs LayerNorm

  • BatchNorm: normalizes across the batch dimension (like making sure the whole class scores around the same average).
  • LayerNorm: normalizes across the features of each sample (like making sure each student individually is balanced, regardless of what others are doing).

Translation:

  • BatchNorm cares about the crowd
  • LayerNorm cares about the individual

Why LayerNorm is Perfect for Transformers

In NLP, batch sizes can be small or variable (sometimes you only have one sentence). If you rely on BatchNorm, it might panic:

“Wait… only one sample? I can’t compute a batch mean!” 😱

LayerNorm saves the day because it says:

“No worries, I’ll just normalize this one sample across its features.”

Intuition

Imagine you have 32 samples, each with 100 features (like 100 different personality traits per person 😅).

LayerNorm goes row by row:

  • Takes one sample
  • Computes the mean and variance across its 100 features
  • Normalizes them (so each person is “centered” and “scaled”)
  • Then applies two trainable parameters, gamma (scale) and beta (shift), to let the model re-learn useful distributions

It’s like giving everyone a personalized adjustment:

  • First, “Hey, let’s calm down your extremes”
  • Then, “Okay, but if blue hair or loud laughter is important, I’ll give it back via gamma and beta.”

Our Custom LayerNorm Implementation

class LayerNorm1d: # (used to be BatchNorm1d)
  def __init__(self, dim, eps=1e-5, momentum=0.1):
      self.eps = eps
      self.gamma = torch.ones(dim)
      self.beta = torch.zeros(dim)
    def __call__(self, x):
      # calculate the forward pass
      xmean = x.mean(1, keepdim=True)   # mean per sample
      xvar = x.var(1, keepdim=True)     # variance per sample
      xhat = (x - xmean) / torch.sqrt(xvar + self.eps) # normalize
      self.out = self.gamma * xhat + self.beta
      return self.out
    def parameters(self):
      return [self.gamma, self.beta]

Testing it:

torch.manual_seed(1337)
module = LayerNorm1d(100)
x = torch.randn(32, 100) # 32 samples, 100 features each
x = module(x)
x.shape

Output:

torch.Size([32, 100])

LayerNorm in Action

Now let’s peek at the effect:

x[:,0].mean(), x[:,0].std()

Output:

(tensor(0.1469), tensor(0.8803))

Across the batch dimension, things are not normalized.

But…

x[0,:].mean(), x[0,:].std()

Output:

(tensor(-9.5367e-09), tensor(1.0000))

Within a single sample, features are perfectly normalized: mean ≈ 0, std ≈ 1.

Key Insight

  • BatchNorm: makes sure the crowd is balanced.
  • LayerNorm: makes sure each individual is balanced.

That’s why Transformers always use LayerNorm. Each token’s feature vector gets normalized independently, which keeps learning stable even with tiny or unpredictable batch sizes.

In simple words:

LayerNorm = “Everyone gets their own z-score makeover.”

Training a Mini-Transformer From Scratch

Okay, here’s where the real fun begins.

We’re no longer just doodling with toy models — this is us building a baby GPT from scratch. It’s like raising a Tamagotchi, except instead of feeding it snacks, we feed it tokens and watch it slowly learn language.

Setting the Ground Rules (Hyperparameters)

Think of these as the “parenting rules” for our little model:

batch_size = 16   # sequences processed in parallel
block_size = 32   # max context length
max_iters = 2000
eval_interval = 100
learning_rate = 1e-3
n_embd = 64       # embedding dimension
n_head = 4        # number of attention heads
n_layer = 4       # number of transformer blocks
dropout = 0.0
  • batch_size (16): How many sentences it reads at once.
  • block_size (32): How much “context window” it can peek at.
  • n_embd (64), n_head (4), n_layer (4): How big its “brain” is — more neurons, more focus, more reasoning.
  • learning_rate (1e-3): The “curiosity knob” — how aggressively it updates itself.

Tokenization: Teaching the Alphabet

Before our model learns to write poetry, it first has to know the alphabet.

We map every unique character into numbers:

chars = sorted(list(set(text)))
stoi = { ch:i for i,ch in enumerate(chars) }
itos = { i:ch for i,ch in enumerate(chars) }
encode = lambda s: [stoi[c] for c in s]
decode = lambda l: ''.join([itos[i] for i in l])
  • encode: letters → numbers.
  • decode: numbers → letters.

Data is split: 90% for training, 10% for validation (because every child needs homework and exams).

Batching: The Meal Plan

The model doesn’t eat the whole dataset at once (that would be like swallowing a dictionary). Instead, it gets bite-sized snacks:

def get_batch(split):
    data = train_data if split == 'train' else val_data
    ix = torch.randint(len(data) - block_size, (batch_size,))
    x = torch.stack([data[i:i+block_size] for i in ix])
    y = torch.stack([data[i+1:i+block_size+1] for i in ix])
    return x.to(device), y.to(device)

Each x is a string of characters, and each y is the "what comes next" target. Simple.

Building the Brain

Here comes the Transformer LEGO set:

  • Head → one little attention unit.
  • MultiHeadAttention → multiple heads working in parallel (like having a group chat).
  • FeedForward → a mini-MLP that adds spice.
  • Block → attention + MLP + normalization + shortcuts (residuals).

All stacked together inside:

self.token_embedding_table = nn.Embedding(vocab_size, n_embd)
self.position_embedding_table = nn.Embedding(block_size, n_embd)
self.blocks = nn.Sequential(*[Block(n_embd, n_head) for _ in range(n_layer)])
self.ln_f = nn.LayerNorm(n_embd)
self.lm_head = nn.Linear(n_embd, vocab_size)

This is our Mini GPT skeleton.

Time to let the kid learn.

for iter in range(max_iters):
